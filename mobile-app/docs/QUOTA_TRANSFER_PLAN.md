# Quota Transfer — "Send GB to a friend" (technical plan)

Status: **PLAN ONLY — not implemented.** Target: v0.9.31+ (after the v0.9.30 UI batch).
Decision: implementation is not "very small and safe" (new money-like ledger, atomicity,
anti-fraud), so per instruction nothing in this document is wired into the app or backend yet.

## 1. Product summary

A user with paid/earned quota can send part of it to another SetaLink user, identified by
SetaLink ID (`SL-227-XXXXXXXX`) or by scanning the friend's QR code. Use case: one user pays
with crypto on behalf of friends who pay him cash, then distributes GB in-app.

## 2. Core rules (from requirements)

- Welcome/free starter quota (1 GB) is **never** transferable.
- `transferable = quota_bytes_total − quota_bytes_used − welcome_bytes − pending_outgoing_transfers`
  (clamped to ≥ 0; `welcome_bytes` = 1 GiB constant, already exposed per-device by the
  entitlement API as of the v0.9.30 batch).
- Deduct from sender and credit receiver **atomically** (single SQLite transaction).
- Minimum transfer: 500 MB (constant `MIN_TRANSFER_BYTES = 524288000`; configurable server-side).
- Daily limit: e.g. max 3 transfers and max 5 GB total per sender per rolling 24 h.
- Confirmation screen before sending; transfer history for both sides; admin audit log;
  anti-fraud flags on suspicious patterns.

## 3. Backend (public/api.php + setalink.db)

### 3.1 Schema

```sql
CREATE TABLE IF NOT EXISTS quota_transfers (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    transfer_code   TEXT UNIQUE,            -- idempotency key generated by the client
    from_device_id  TEXT NOT NULL,
    to_device_id    TEXT NOT NULL,
    amount_bytes    INTEGER NOT NULL,
    status          TEXT DEFAULT 'completed',  -- completed | reversed | held
    note            TEXT DEFAULT '',
    from_ip         TEXT DEFAULT '',
    user_agent      TEXT DEFAULT '',
    fraud_score     INTEGER DEFAULT 0,
    fraud_flags     TEXT DEFAULT '[]',
    created_at      TEXT DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_qt_from ON quota_transfers(from_device_id, created_at);
CREATE INDEX IF NOT EXISTS idx_qt_to   ON quota_transfers(to_device_id,   created_at);
```

No `pending` money state in v1: transfers are synchronous (`completed`) unless the fraud
gate holds them (`held` — quota deducted from sender, credited to nobody until admin
approves/reverses, mirroring the referral `pending` pattern). `reversed` is admin-only.

### 3.2 Endpoints (mobile, `?mobile=1`)

**`POST action=transfer-quota`**
Params: `device_id` (sender), `to_user_id` (SL-… ID, case-insensitive) **or**
`to_device_id`, `amount_bytes`, `note` (≤120 chars), `transfer_code` (UUID for idempotency).

Validation order, all inside `BEGIN IMMEDIATE` transaction:
1. Idempotency: if `transfer_code` already exists → return that row (prevents double-send on retry).
2. Sender exists, not blocked; receiver resolved by `user_id` (exact, upper-cased) and exists,
   not blocked, `to != from` (also compare `android_id_hash` — same hardware ⇒ reject).
3. `amount_bytes >= MIN_TRANSFER_BYTES` and multiple of 1 MB.
4. Recompute transferable server-side (never trust client):
   `transferable = max(0, total − used − 1GiB − SUM(held outgoing))`. Reject if exceeded.
5. Daily limits: `COUNT(*) < 3` and `SUM(amount_bytes) + amount <= 5 GiB` over last 24 h.
6. Fraud scoring (reuse referral heuristics): same IP as receiver (+30), receiver created
   < 24 h ago (+20), > N distinct receivers in 7 days (+30), round-trip pattern
   (receiver previously sent to sender, +40). Score ≥ 70 ⇒ `status='held'`.
7. Apply: `UPDATE devices SET quota_bytes_total = quota_bytes_total − ? WHERE device_id = ?`
   (sender) and, when not held, `… + ? …` (receiver). Insert ledger row. COMMIT.

Response: `{status, transfer_id, amount_bytes, new_transferable_bytes}`.
Important: deduct from **total**, not add to used — keeps `report-session` (single quota
writer for usage) untouched and the BandwidthBar math correct on both devices.

**`GET action=transfer-history`** — `device_id`, returns last 50 rows where device is
sender or receiver, with direction, masked counterpart user_id, amount, status, note, date.

**Entitlement responses** gain `transferable_bytes` so the app shows the sendable balance
without client-side math drift.

### 3.3 Admin

- New "Transfers" section in admin panel: full audit table (IP, UA, fraud flags), filter by
  status, actions: approve `held` (credit receiver), reverse `completed` (return to sender,
  clamp if receiver already consumed).
- Audit log: every transfer row is itself the audit record; admin actions append to the
  existing admin action log.

### 3.4 Race-condition note

SQLite + `BEGIN IMMEDIATE` serializes writers, so the check-then-update inside one
transaction is sufficient. The receiver credit and sender debit must be in the same
transaction — never two requests.

## 4. App (React Native)

- **Entry point**: "Send GB" card on Profile (only rendered when `transferable_bytes > 0`).
- **SendQuotaScreen** (new stack route, `slide_from_right`):
  - Friend ID input with `SL-` mask + paste button.
  - QR scan button → scans friend's existing referral/profile QR. The Profile QR payload
    today is the referral URL; extend it to `setalink://u/<USER_ID>?ref=<CODE>` so one QR
    serves both invite and transfer (old QR remains parseable: fall back to ref-code lookup).
    Requires a camera/QR dependency (e.g. `react-native-vision-camera` or
    `react-native-camera-kit`) — **new native dep ⇒ needs a real APK build + size check**,
    one more reason this is not in v0.9.30. v1 fallback: manual ID entry only, QR in v1.1.
  - Amount selector: slider/stepper 0.5–transferable GB, quick chips (1/2/5 GB), optional note.
  - Confirmation modal: receiver ID echo-back (and receiver's masked country/flag from a
    `resolve-user` endpoint so the sender can verify before committing), amount, fee-free note.
  - Result + updated balances; deep-link the receiver via inbox message
    ("You received X GB from SL-…") using the existing admin_messages pipeline.
- **TransferHistory**: section inside SendQuotaScreen (or Activity tab) listing
  `transfer-history` rows; sent = red/−, received = green/+.
- **Store**: `transferStore` (no persistence needed beyond cache) + `entitlementService`
  functions `transferQuota()`, `getTransferHistory()`, `resolveUser()`.
- After a successful transfer call `syncEntitlement()` to refresh quota numbers.

## 5. Anti-abuse summary

| Control | Where |
|---|---|
| Welcome 1 GB excluded | server-side transferable formula |
| Min 500 MB / 1 MB granularity | server validation |
| 3 transfers / 5 GB per 24 h | server validation |
| Same-hardware & same-IP detection | fraud score |
| Round-trip / fan-out patterns | fraud score → `held` |
| Idempotency on retries | `transfer_code` unique key |
| Admin reverse/approve + full audit | admin panel |

## 6. Open questions for product owner

1. Should the *receiver's* received GB become transferable again (re-transfer chains enable
   laundering of referral bonuses) — recommendation: **received GB is NOT re-transferable**
   (track `received_transfer_bytes` and subtract it in the transferable formula).
2. Are referral-earned GB transferable, or only purchased? Current formula allows referral GB
   (everything above welcome). If only purchased, subtract referral_bytes too.
3. Exact daily limits and fraud threshold values.
4. QR in v1 or v1.1 (native camera dependency / APK size).

## 7. Effort estimate

Backend (endpoints + admin page): ~1 day. App (screen, store, confirm flow, history): ~1–2 days.
QR scanning (native dep + build + test on arm32): +1 day. Test matrix: idempotent retry,
